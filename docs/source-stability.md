# 数据源稳定链路

目标不是“源越多越好”，而是**每一次调研都知道哪个源活着、哪个死了、死了之后走哪条路**。

## 1. 分层定义

- **A 已实测**：本轮或最近一次健康检查中，脚本返回 XML 且条目日期新鲜。可用作常规信号源。
- **B 文档记载**：官方订阅中心、搜索清单或 RSSHub 文档给出的地址，本轮未逐条实测。引用前必须先测 1 条；测通才算当轮可用，测不通走回退。
- **C 已确认失效**：实测返回 403、404、HTML 安全检测页、路由不存在等。**移出常规清单**，只保留在 `sources.yaml` 里做“不要再用”的记录，直到一次新的实测通过才可复活。
- **D 无稳定 RSS**：不编 feed 地址。走平台页、站内搜索、浏览器核查。

截至 2026-10-29 的 C 层实例（之后以实测为准）：

- `rsshub.app/zhihu/hotlist`：文本抓取 403；浏览器实测能打开 rsshub.app，但路由返回“不存在或已被删除”，无条目。
- `https://36kr.com/feed`：直接抓取返回安全检测页，非 XML；第三方监测亦称自 2026-08-05 起不响应。

## 2. 每个源的回退链（按顺序，不跳级编造）

```
官方直连 feed
  → RSSHub 现行路由（当轮实测通过）
  → 另一公开 RSSHub 实例 / 自建实例
  → 平台页 via 浏览器 / 站内搜索
  → 标注“本轮未拿到 + 失败原因”
```

回退时要记录走到了哪一级。报告里写“36氪 RSS”就必须真的是从 RSS 拿到的；如果实际是走站内搜索拿到的，就写站内搜索。

## 3. RSSHub 特别规则

RSSHub 是基础设施，不是某个源的保证：

- 实例健康度差异极大（公开实例的 uptime、缓存命中、热门路由每天都在变）。
- 路由会改名、删除（知乎热榜路由就是实例）。每次用路由前，先看 RSSHub 最新文档，再实测。
- 遇到 Cloudflare 质询、403，不要循环重试；换实例或走页面，失败原因写进未拿到清单。
- 自建实例是最稳的长期解，但本仓库不替用户做部署决策；需要时按 RSSHub 官方文档自建。

## 4. 每周健康检查

```bash
python3 scripts/check_feeds.py --config skills/muse-global-research/sources.yaml
```

- 连续两周失败的 A/B 源 → 降级为“维修中”，移出常规清单，保留在 `sources.yaml` 的 C 层记录里。
- 复活条件：一次新的完整实测通过（XML + 新鲜条目），并更新 `verified_on`。
- 不要静默保留死链：清单里出现的每个源，要么是当轮可用的，要么明确标着失败原因。

## 5. 新鲜度判断

- RSS 条目以 `pubDate` / `published` / `updated` 为准；无日期的条目写“日期未标注”，不写“今日”。
- 热榜、平台页以页面本身显示的时间为准；抓取时间不是事件时间。
- “最新”这个词在报告里必须配一个日期，否则删掉。
